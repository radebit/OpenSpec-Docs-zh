命令参考

工作流与调用方式

以下 /opsx: 写法与对话示例均为 Claude Code 的示意，并非实测输出或所有工具的统一语法。其他工具见调用方式。

默认快速路径（core profile）
/opsx:propose创建变更并一键生成规划产物
/opsx:explore在提交变更前思考和探索想法
/opsx:apply实现变更中的任务
/opsx:update原地修订现有规划产物
/opsx:sync将 Delta 规范合并到主规范
/opsx:archive归档已完成的变更
扩展工作流命令（自定义选择）
/opsx:new创建新变更脚手架
/opsx:continue按依赖顺序创建下一个产物
/opsx:ff快进：一次创建所有规划产物
/opsx:verify验证实现是否与产物匹配
/opsx:bulk-archive批量归档多个变更
/opsx:onboard引导式完整工作流教程
/opsx:propose
core profile

创建新变更并一步生成所有规划产物。这是 core profile 中的默认启动命令。

语法 /opsx:propose [变更名或描述]
参数必填描述
change-name-or-description否kebab-case 名称或自然语言描述
Claude Code 对话示意（非实测）
You: /opsx:propose add-dark-mode

AI:  已创建 openspec/changes/add-dark-mode/
     ✓ proposal.md
     ✓ specs/ui/spec.md
     ✓ design.md
     ✓ tasks.md
     规划已生成，请先审查。此处停止，不开始实现。
     审查后由你另行授权 /opsx:apply。
propose 只获授权生成规划，即使最初要求“构建”也不会接着写代码。先只读检查相关代码、测试与文档，再按当前 Schema 的指令生成产物。若需逐步审查，启用扩展工作流并使用 /opsx:new + /opsx:continue。
/opsx:explore
core profile

在提交变更之前，思考想法、调查问题、澄清需求。

语法 /opsx:explore [话题]
Claude Code 对话示意（非实测）
You: /opsx:explore

AI:  你想探索什么？

You: 如何为移动端应用处理身份验证？

AI:  让我来研究你当前的认证设置...
     [分析代码库]

     我看到你在 Web 端使用了基于 session 的认证。
     对于移动端，我们有三种主要选择：

     1. JWT 令牌（无状态，支持离线）
     2. OAuth2（如需第三方登录）
     3. 扩展当前 session（更简单，但需要连接）

     你的 API 已经配置了 CORS。你对哪个方向感兴趣？

You: 让我们用 JWT。能开始一个变更吗？

AI:  你已授权开始变更，我会在本次探索中创建脚手架并展示状态。
     若还需记录规划，请明确指定产物；不会开始实现。
默认只研究。用户明确授权后，可在当前会话中 capture 变更或指定规划产物，不必另发工作流命令。自定义 Schema 只记录到其定义的产物，捕获规划不等于授权实现。
/opsx:new
扩展工作流

创建新变更脚手架。创建变更文件夹，等待你用 /opsx:continue 或 /opsx:ff 生成产物。

语法 /opsx:new [变更名] [--schema <schema-name>]
Claude Code 对话示意（非实测）
You: /opsx:new add-dark-mode

AI:  已创建 openspec/changes/add-dark-mode/
     Schema: spec-driven

     准备创建: proposal
     使用 /opsx:continue 创建，或 /opsx:ff 创建所有产物。
使用描述性名称：add-feature、fix-bug、refactor-module。避免使用 update、changes、wip 等泛称。
/opsx:continue
扩展工作流

在依赖链中创建下一个产物。每次创建一个产物以实现增量进度。

语法 /opsx:continue [变更名]
Claude Code 对话示意（非实测）
You: /opsx:continue

AI:  变更: add-dark-mode

     产物状态:
     ✓ proposal    (完成)
     ◆ specs       (就绪)
     ◆ design      (就绪)
     ○ tasks       (阻塞 - 需要: specs、design)

     正在创建 specs...
     ✓ 已创建 openspec/changes/add-dark-mode/specs/ui/spec.md

     现在可用: design；tasks 仍需等待 design。
     运行 /opsx:continue 创建下一个产物。
每次只推进一个产物，按 Schema 的依赖及声明顺序选择。默认 specs glob 任一文件存在即可显示 done，仍需检查提案中的 capability 是否全部覆盖，补齐后再推进。现有规划的一致性修订用 /opsx:update。
/opsx:ff
扩展工作流

快进产物创建。一次生成 apply 所需规划及其依赖，完成后停止等待审查与实现授权。

语法 /opsx:ff [变更名]
Claude Code 对话示意（非实测）
You: /opsx:ff add-dark-mode

AI:  快进 add-dark-mode...

     ✓ 创建 proposal.md
     ✓ 创建 specs/ui/spec.md
     ✓ 创建 design.md
     ✓ 创建 tasks.md

     apply 所需规划已生成，请先审查。
     只有另行授权 /opsx:apply 后才开始实现。
ff 创建 apply 所需产物及其传递依赖，并非无条件创建 Schema 的所有可选产物。生成前只读检查项目，遵循各产物的 instruction、模板与依赖；若指令委托其他 skill，只能在已核对的输出路径内执行。快进不省略审查，也不自动授权实现。
/opsx:apply
core profile

实现变更中的任务。逐步处理任务列表，编写代码并勾选完成项。

语法 /opsx:apply [变更名]
Claude Code 对话示意（非实测）
You: /opsx:apply

AI:  实现 add-dark-mode...

     读取 tasks.md:
     - [ ] 1.1 创建 ThemeContext；验证：主题切换单元测试通过
     - [ ] 1.2 添加 CSS 自定义属性；验证：页面两种主题显示正确
     - [ ] 1.3 实现 localStorage 持久化；验证：刷新后主题保持

     处理 1.1: 创建 ThemeContext 并运行指定测试...
     [创建 src/context/ThemeContext.tsx]
     ✓ 1.1 完成，更新对应 sourcePath、line 的复选框

     处理 1.2: 添加 CSS 自定义属性并检查页面显示...
     [更新 src/styles/globals.css]
     ✓ 1.2 完成，重新读取进度
     ...
     全部任务完成后：建议审查或验证，不自动运行 verify 或归档。
  • 缺少 Delta：Schema 定义了 specs、没有 Delta 且未设置 skip_specs: true 时，apply 给出警告。警告不改变 apply.requires 门槛，也不代表规范合格；应先补齐或明确有意跳过。
  • 逐任务验证：默认 tasks 指令要求每项写明测试、命令、可观察行为或交付物。只在指定行为完整实现后打勾，不以部分实现、延后或缩减范围冒充完成。
  • 状态与恢复：读取当前 Schema 的 contextFiles 与 apply 指令。按返回的 sourcePath、line 核对并修改复选框，再刷新进度；blocked、错误或新增范围时暂停。
完成复选框只代表跟踪任务完成，不等于验证通过或可直接归档。apply 完成后只建议审查或验证，/opsx:verify 需先启用并由用户调用。
/opsx:update
core profile

原地逐项修订现有规划产物，检查提案、规范、设计与任务之间的矛盾，不重建变更，不编写实现代码。

语法 /opsx:update [变更名]
  • 逐项确认：读取当前 status 的 Schema、产物 ID 与 existingOutputPaths，先在对话中展示每项修订及原因，用户确认后才写入。拒绝的项保持原样，前后依赖都可回查。
  • 保留进度：不 reset 已打勾任务，不把规划修订当成重建。修订涉及代码时，只提示重新授权 apply；不自动实现、验证或归档。
  • 缺失产物：完全没有文件的 ready/blocked 产物交给已启用的 continue，或按 openspec instructions <artifact-id> --change <name> --json 另行创建。skipped 产物保持不动。
  • 部分 glob 例外：已有文件的 glob 产物可补缺失 capability 文件。先取当前指令、模板、规则与依赖，逐项确认；创建前刷新并核对具体路径在 changeRoot 内、匹配 glob 且不存在，不向 glob 字符串写入，也不覆盖已有文件。
Claude Code 对话示意（非实测）
You: /opsx:update add-dark-mode
     请把主题偏好改为跟随系统，并协调现有规划。

AI:  建议先修改 design 的默认策略，再修订 specs 的对应场景。
     我会分别展示差异并等待确认；现有任务勾选状态不重置。

You: 先确认 design 的修改。

AI:  仅写入已确认的 design 修订，其他项等待确认。
     若需调整实现，请审查后另行授权 apply。
不是终端命令：openspec update 刷新工具集成文件；/opsx:update（skill：openspec-update-change）修订变更规划。若变更意图已根本改变，应另建变更。
/opsx:verify
扩展工作流

验证实现是否与变更产物匹配。从完整性、正确性和一致性三个维度检查。

语法 /opsx:verify [变更名]
维度验证内容
完整性所有任务完成、所有需求已实现、场景已覆盖
正确性实现与规范意图匹配、边缘情况已处理
一致性设计决策在代码中有体现、模式一致
Delta 操作验证基准
ADDED按 Delta 的新需求及场景查实现和测试。
MODIFIED按 Delta 的新文本验证，不以主规范旧文本代替。
REMOVED先按大小写敏感、精确规范化名称从主规范读取原需求正文与场景。已同步移除时，从同一路径的规划仓库 Git 历史恢复 baseline，再检查旧行为是否消失，不能只搜标题。
RENAMED读取主规范 FROM 的 baseline；已同步时可读 TO，检查行为保持。TO 同时 MODIFIED 时按修改后的文本验证，不要求代码符号改名。
Claude Code 对话示意（非实测）
You: /opsx:verify

AI:  验证 add-dark-mode...
     任务完成：8/8（只说明跟踪任务完成）
     ADDED/MODIFIED：检查实现与场景，记录文件、行号及证据
     REMOVED：主规范与同路径历史均无可用 baseline
     Spec Coverage：Not verified（该移除项无法验证，不计 PASS）
     一致性：记录设计偏差与建议

     总结：已执行检查未发现关键问题，但仍有未验证项。
     不宣称全部通过或已可归档，不在此执行实现或归档。
缺失、不可读或只复述标题的 baseline 都是 Not verified，不是 PASS。自定义产物按 status 的路径和 Schema 指令读取，任务按 apply.tracks 聚合；未定义或有意跳过的检查为 Not applicable。仅移除/改名的变更，正确性中的实现映射与场景覆盖不适用，baseline 检查仍保留。verify 是建议性检查，不新增归档硬门槛。
/opsx:sync
core profile

将变更中的 Delta 合并到主规范，保留活跃变更。sync 属于 core 工作流，可在归档前提前同步规范。

语法 /opsx:sync [变更名]
操作合并与已同步判定
ADDED加入新需求；主规范已含目标内容时 no-op。
MODIFIEDDelta 必须带完整需求正文与所有保留场景。合并描述、场景变化并保留未提及内容；目标内容已一致时 no-op，不能用片段替换整块而丢失场景。
REMOVED删除整个需求；已消失时 no-op。最后一个需求的删除须满足 retire_capabilities: true 等退休条件，否则阻塞，不留下空规范。
RENAMEDFROM 改为 TO；TO 存在且 FROM 不存在时已同步。
  • 输入与路径：只从 status 的 artifactPaths.specs.existingOutputPaths 读取 Delta，主规范写到 planningHome.root/openspec/specs/。没有 specs 产物或没有输出时，不从其他产物猜测。
  • 规则与验证：写入前读取当前 openspec instructions specs --change <name> --json；查询失败或 JSON 无效须停。合并后运行 openspec validate --specs，有阻塞、验证失败或内容未对齐时，不报告成功，也不得继续归档移动。
  • 保留 Delta：四种操作已全部同步时可 no-op，仍保留变更里的 Delta。新主规范只能从 ADDED 创建，缺失基准时不能凭空应用 MODIFIED/RENAMED。
sync 是规范内容合并，不是 Git 同步，不执行 commit、push 或 pull。直接归档时，可经用户确认在同一会话 inline sync，不必另发 /opsx:sync。
/opsx:archive
core profile

归档已完成的变更。完成变更并将其移至归档文件夹。

语法 /opsx:archive [变更名]
Claude Code 对话示意（非实测）
You: /opsx:archive

AI:  归档 add-dark-mode...

     产物状态:
     ✓ proposal.md 存在
     ✓ specs/ 存在
     ✓ design.md 存在
     ✓ tasks.md 存在 (8/8 任务完成)

     任务已打勾，但仍需检查产物、规范状态与归档目标。
     Delta 规范: 尚未同步
     → 在当前会话同步后归档？(推荐)

You: 是

AI:  在同一会话 inline sync，等待完成，不另发命令或后台运行。
     ✓ 已将规范同步到 openspec/specs/ui/spec.md
     对照四种 Delta 操作并确认验证无阻塞后：
     ✓ 已移至 openspec/changes/archive/2026-03-10-add-dark-mode/

     变更归档成功。
任务全勾不等于可归档。未完成产物/任务先警告并询问；同步选择也由用户决定，可明确选择不同步。不得静默解决冲突。选定同步后，失败、验证阻塞或内容不匹配必须停归档，目标重名也不移动，不以“任务已完成”绕过。
/opsx:bulk-archive
扩展工作流

批量检查并归档多个变更。先调查同一 capability 路径上的冲突，展示实现证据、同步取舍与顺序，用户确认后才执行。

语法 /opsx:bulk-archive [变更名...]
Claude Code 对话示意（非实测）
You: /opsx:bulk-archive

AI:  找到 3 个候选变更（复选框完成不等于可归档）:
     - add-dark-mode (8/8 任务完成)
     - fix-login-bug (3/3 任务完成)
     - update-footer (2/2 任务完成)

     检查规范冲突...
     ⚠ add-dark-mode 和 update-footer 都触及 specs/ui/

     先核对代码与测试，展示各 Delta 的证据。
     建议仅在两者都已实现时按旧到新合并；未实现的 Delta 排除并警告。
     请确认该取舍、顺序与归档范围；未确认前不改主规范。

You: 确认方案，只归档检查通过的变更。

AI:  先取得本批次全部所需 specs 指令，再在当前会话逐项 inline sync。
     同步完成后对照确认纳入的 Delta，失败或未解决冲突的变更保留原位。
     ✓ 已归档 add-dark-mode
     ✓ 已归档 fix-login-bug
     ✓ 已归档 update-footer
不能无询问自动解决冲突，也不能仅凭勾选或创建时间覆盖规范。按用户确认的每个 Delta 取舍同步；任何所需指令查询失败，在全批写入/移动前停止。执行中某项同步失败或验证阻塞，该变更不移动，记录 Failed；重名目标也不覆盖。报告成功、跳过、失败及仍未同步的 Delta。
/opsx:onboard
扩展工作流

完整工作流的引导式入门教程，使用你的真实代码库进行交互式演示。

语法 /opsx:onboard
📋
包含 11 个阶段
欢迎与代码库分析 → 发现改进机会 → 创建变更 → 编写提案 → 创建规范 → 编写设计 → 创建任务 → 实现任务 → 验证实现 → 归档变更 → 总结与后续步骤
适合首次使用 OpenSpec 的用户。使用真实代码，不是玩具示例。完整完成约需 15-30 分钟。
