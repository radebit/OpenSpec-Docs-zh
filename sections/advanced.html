工作流

常见工作流模式

按场景选择工作流。此页 /opsx: 调用示意使用 Claude Code 写法，其他工具见调用方式。

默认快速路径（core profile）
/opsx:propose → /opsx:apply → /opsx:sync → /opsx:archive

新安装默认 core：propose、explore、apply、update、sync、archive，共六个工作流。规划生成后先审查，再授权 apply；任务完成不自动 verify 或归档。

扩展工作流（自定义选择）
/opsx:new → /opsx:ff → /opsx:apply → /opsx:verify → /opsx:archive
启用扩展工作流
openspec config profile
openspec update

new、continue、ff、verify、bulk-archive、onboard 需在 custom profile 中启用，再运行终端 openspec update 刷新集成。

⚡ 快速功能（清晰需求）
/opsx:new → /opsx:ff → /opsx:apply → /opsx:verify → /opsx:archive

适用于：中小型功能、Bug 修复、直接明了的变更

🔍 探索式（需求不明确）
/opsx:explore → /opsx:new → /opsx:continue → ... → /opsx:apply

适用于：性能优化、调试、架构决策、需求不清晰

🔀 并行变更（多任务）
变更 A 进行中时 → 切换上下文 → 同时处理变更 B → /opsx:bulk-archive

适用于：并行工作流、紧急中断、团队协作。批量归档先展示冲突方案并确认，不凭任务全勾自动归档。

原地规划修订（已有变更）
发现规划矛盾 → /opsx:update → 逐项确认修订 → 审查 → 另行授权 /opsx:apply

只修订现有规划，不写实现代码、不重建、不重置已勾任务。部分 glob 的缺失 capability 可确认后补齐；完全缺失产物另行创建。终端 openspec update 是刷新集成，不是此路径。

何时使用 /opsx:ff 还是 /opsx:continue

场景推荐使用
需求清晰，准备构建/opsx:ff
探索中，想逐步审查/opsx:continue
想在创建规范前迭代提案/opsx:continue
时间紧迫，需要快速推进/opsx:ff
复杂变更，需要精细控制/opsx:continue
经验法则：如果你能预先描述完整范围，使用 /opsx:ff。如果你在过程中摸索，使用 /opsx:continue。

最佳实践

01

保持变更聚焦

每个变更对应一个逻辑工作单元。"添加功能 X 同时重构 Y"应考虑拆成两个独立变更。

02

需求不明确时使用 explore

默认只研究；明确授权后可在当前探索中捕获指定规划产物。捕获规划不授权实现，自定义 Schema 不创建其未定义的文件。

03

归档前先 verify

启用扩展 /opsx:verify 后检查实现与产物。缺少适用证据或 baseline 就是未验证，不计 PASS；这是建议性检查，不新增归档硬门槛。

04

清晰命名变更

好名称让 openspec list 更有用：add-dark-mode、fix-login-redirect、implement-2fa。避免 feature-1、update、wip。

定制化

让 OpenSpec 按你的方式工作

三个级别的自定义，满足从个人到企业的不同需求

级别用途最适合
项目配置设置默认值、注入上下文/规则大多数团队
自定义 Schema定义你自己的工作流产物有独特流程的团队
全局覆盖跨所有项目共享 Schema高级用户

项目配置（openspec/config.yaml）

用项目配置保存默认 Schema、持久约束与文档指针，不把代码库快照塞进 context。

  • schema：设置默认工作流，省去每次传入 --schema。
  • context：所有产物的共同项目约束；apply/archive 执行时也读取当前值。代码事实按需查源码，项目说明放文档并保留指针。
  • rules：以 artifact ID 为键的字符串数组，只约束对应产物内容，不是执行步骤。
  • operations：只支持 apply、archive 的 guidance 字符串数组，提供执行建议，不改变产物规则或 CLI 状态。
openspec/config.yaml
schema: spec-driven

context: |
  公共 API 必须保持向后兼容，破坏性变更需明确批准。
  项目架构见 docs/architecture.md，API 约定见 docs/api.md。
  测试与开发约定见 CONTRIBUTING.md，代码事实按需读取源码。

rules:
  proposal:
    - 包含回滚计划
    - 确认受影响的团队
  specs:
    - 使用 Requirement 和 Scenario 结构标题
    - 在发明新模式之前引用现有模式

operations:
  apply:
    guidance:
      - 先运行相关测试，再运行全量测试
  archive:
    guidance:
      - 保持完成总结简短
示例中的文档路径需换成项目实际路径。执行时 context 与 operationGuidance 分开返回；建议与内置流程、用户选择或 CLI 控制值冲突时不执行并说明，不能据此跳过 blocked 状态或证明任务完成。除非另有授权，不把这些文本复制进产物或代码。

遗留 openspec/project.md：先人工 review，将持久约束和文档指针迁入 config.yaml，项目说明留在项目文档。init/update 不自动迁移或删除该文件，核对后再决定保留或移除。

自定义 Schema

自定义 Schema 定义产物、模板和依赖。工作流必须跟随当前指令，不假定固定的 proposal/specs/design/tasks 文件。

  • 声明顺序：requires 决定哪个产物可创建；多个产物同时 ready 时，按 artifacts 声明顺序选择。
  • apply.requires：只能引用已声明的 artifact ID。非法 ID 在加载 Schema 时即报错，不再静默跳过。
  • instruction：每次读取当前 openspec instructions <artifact-id> --change <name> --json，遵循指令、模板和依赖；指令委托 skill/command 时也须遵守已核对的输出路径。
  • apply.tracks：是文件路径，可用 glob，不是 artifact ID。建议与某产物的 generates 完全一致；不一致时 schema validate 警告，apply 仍读取该路径，list/status 的进度可能回退到 tasks.md。
bash — Fork 现有 Schema
openspec schema fork spec-driven my-workflow

或从头创建：

openspec/schemas/rapid/schema.yaml — 快速迭代工作流示例
name: rapid
version: 1
description: 最小开销的快速迭代

artifacts:
  - id: proposal
    generates: proposal.md
    description: 快速提案
    template: proposal.md
    instruction: |
      为此变更创建简短提案。
      重点说明做什么和为什么，跳过详细规范。
    requires: []

  - id: tasks
    generates: tasks.md
    description: 实现清单
    template: tasks.md
    requires: [proposal]

apply:
  requires: [tasks]
  tracks: tasks.md
bash — 添加审查步骤的 Schema 示例
# Fork 默认 Schema 并添加审查步骤
openspec schema fork spec-driven with-review

# 然后编辑 schema.yaml 添加:
  - id: review
    generates: review.md
    description: 实现前的审查清单
    template: review.md
    instruction: |
      基于设计创建审查清单。
      包含安全、性能和测试注意事项。
    requires:
      - design

# 在已有 tasks 的 requires 中补入 review，保留其他配置:
# requires: [specs, design, review]

# 添加 templates/review.md 后，核对模板、引用及依赖图
openspec schema validate with-review
review 片段放进 artifacts 列表，并添加它引用的模板。只加 review 而不把它接入 tasks/apply 依赖链，不会阻止实现。默认 tasks 同时依赖 specs 与 design，补 review 时不能丢掉原依赖。

非交互式安装

用于 CI/CD 或脚本化安装，可使用 --tools 和 --profile 参数：

bash
# 配置特定工具
openspec init --tools claude,cursor

# 配置所有支持的工具
openspec init --tools all

# 跳过工具配置
openspec init --tools none

# 指定 profile 覆盖
openspec init --profile core

快速配置

新项目在终端用 openspec init --language "中文（简体）"。已有配置不会被该选项覆盖，需编辑 openspec/config.yaml 的 context，保留其他约束。

正文可用中文，OpenSpec 结构 header（如 Requirement、Scenario）与 SHALL/MUST 关键词保持英文。结构标题是解析锚点，不能随正文一起翻译。
中文（简体）配置示例

context: |
  正文使用简体中文，结构标题与 SHALL/MUST 关键词保持英文。
  保留公共 API 向后兼容性。
  项目约定见 docs/architecture.md（换成项目实际文档路径）。
config.yaml
context: |
  正文使用简体中文。
  OpenSpec 结构标题与 SHALL/MUST 关键词保持英文。

遥测数据

匿名遥测默认采用 opt-out：未配置时启用，首次披露提示展示前不发送数据。事件只含命令名、版本等固定字段与随机匿名 ID，不含参数、路径或内容。

  • 全局关闭：openspec config set telemetry.enabled false 禁用遥测与联网版本检查，设置写入全局配置，不是项目 config.yaml。
  • 优先级：环境变量 opt-out 与 CI 优先于全局配置，不能用 enabled=true 覆盖。全局配置无法读取时也不发送。
  • 首次披露：--json 延后提示，不设置 noticeSeen；未展示提示前不创建匿名 ID，也不发送遥测。后续非 JSON 调用才展示。
  • Tab 补全：openspec __complete 不记录遥测，不消耗首次披露提示。
终端 — 禁用遥测与版本检查
openspec config set telemetry.enabled false

# 或使用环境变量
export OPENSPEC_TELEMETRY=0
# 或
export DO_NOT_TRACK=1
环境值忽略大小写与首尾空格：OPENSPEC_TELEMETRY 只有 1/true/yes/on 表示不主动关闭；DO_NOT_TRACK 除空值、0/false/no/off 外均关闭。两者任一要求关闭就关闭，开启值不会覆盖其他 opt-out。
