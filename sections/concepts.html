核心概念

理解 OpenSpec 的核心机制

深入了解规范、变更、产物和 Delta 机制如何协同工作

设计哲学

OpenSpec 围绕四个核心原则构建：

🌊

流动而非僵化

传统规范系统将你锁定在阶段中：先规划，再实现，然后完成。OpenSpec 更灵活——你可以以任何有意义的顺序创建产物。

🔄

迭代而非瀑布

需求会变化，理解会加深。最初看起来不错的方案在看到代码库后可能无法成立。OpenSpec 拥抱这种现实。

✨

简单而非复杂

一些规范框架需要大量设置、严格格式或繁重流程。OpenSpec 不挡你的路。几秒钟初始化，立即开始工作。

🏗️

存量项目优先

大多数软件工作不是从零开始，而是在已有系统上迭代改造。OpenSpec 基于 Delta 的方法，让描述"改了什么"变得自然而直观。

整体架构

OpenSpec 将你的工作组织为两个主要区域：

specs/
权威基准
描述系统当前行为
归档时合并
changes/
提议中的修改
每个变更 = 一个文件夹
💡
这种分离允许多个变更并行规划，并在影响主规范前审查。它不保证无冲突：触及同一主规范或需求时仍需协调，合并前必须处理冲突。

Store、References 与 WorksetBeta

Beta 功能：Store、references、context 和 workset 处于测试阶段，命令、文件格式和 JSON 输出可能变化。

将共享规划放在独立仓库，用 references 提供只读上游规范，用 workset 重开本机相关文件夹。

Store
三个不同的职责
store = 在本机按名称登记的独立 OpenSpec 规划 repo
references = 当前根读取的上游 store 规范，不改变命令操作根
workset = 个人保存的本机文件夹视图，不是共享规划状态

Store 结构：沿用仓库本地 openspec/ 布局，另有共享身份文件。登记表仅保存本机映射。

独立规划仓库
team-plans/
├── .openspec-store/
│   └── store.yaml                 # store 身份，随仓库共享
└── openspec/
    ├── specs/                     # 当前行为
    ├── changes/                   # 活跃变更及 archive/
    └── config.yaml                # schema、上下文与规则

先创建并登记 store，再用 --store 选择它。已有 checkout 用 openspec store register <path> 登记。空的 specs/、changes/ 目录可能尚未进入 Git。

终端：选择独立规划根
openspec store setup team-plans --path ~/openspec/team-plans
openspec new change add-login --store team-plans

Git 由你管理：OpenSpec 不会自动 clone、pull、push 或同步规范。共享规划仍需你提交、推送、拉取和审查。命令见 CLI 参考 - Store。

References 只读：保留组件仓库自己的根，在 openspec/config.yaml 声明上游 store。instructions 提供主规范摘要与精确读取命令，不自动读取活跃变更或写入上游。

组件仓库：openspec/config.yaml
schema: spec-driven
references:
  - team-plans

openspec context 列出当前根及其 references。它不自动发现所有组件代码仓库，也不改变根选择。见 CLI 参考 - Context。

store: 指向外置根：若仓库不保存本地规划，只有 config 文件而没有 openspec/specs/ 或 openspec/changes/ 目录，可声明指针：

config-only 仓库：openspec/config.yaml
store: team-plans

根选择顺序：普通工作流命令按以下顺序选择一个根；先找到最近的有效目录，再判断本地规划或指针，不把所有祖先分开排序。

  1. --store <id>：显式选择已登记 store，优先于本地根和指针。
  2. 从当前目录向上找最近的有效 openspec/：有 specs/ 或 changes/ 目录且目录自身不是独立 store 根时，使用本地根，即使目录为空；同时存在的字符串 store: 被忽略并警告。仅有 config 文件时，有 store: 就解析指针，无 store: 仍为本地根。单独的空 openspec/ 目录不算根。
  3. 没有有效目录时，使用全局 defaultStore（openspec config set defaultStore team-plans）。
  4. 仍未选中根：已有登记 store 则报错并提示显式选择；无登记 store 则仅在命令允许隐式根时使用当前目录，否则报错。

参与根选择的显式 store、指针或 defaultStore 解析失败时直接报错，不静默降级到其他根。较近的 config-only 指针也不会被更远的祖先规划根覆盖。

Workset 仅为个人视图：保存本机 checkout 路径并在编辑器中重开。它不选择命令根、不分派跨仓库任务，也不授予代理跨 repo 写权限。

终端：保存并重开本机文件夹
openspec workset create platform \
  --member ~/openspec/team-plans --member ~/src/api-server --tool code
openspec workset open platform
可见性不是授权：workset 不随规划仓库共享，移除 workset 不删除成员文件夹。实现、测试和审查仍需明确各 repo 的范围。见 CLI 参考 - Workset。

规范 (Specs)

规范使用结构化需求和场景来描述系统行为。一个典型的规范文件如下：

openspec/specs/auth/spec.md
# Auth 规范

## Purpose
定义应用程序的身份验证契约与会话边界，让客户端可以依赖一致的登录成功响应、凭据错误处理和令牌颁发行为，不限定服务内部实现方式。

## Requirements

### Requirement: 用户身份验证
系统 SHALL 在登录成功时颁发 JWT 令牌。

#### Scenario: 有效凭据
- GIVEN 用户具有有效凭据
- WHEN 用户提交登录表单
- THEN 返回 JWT 令牌
- AND 用户被重定向到仪表板

#### Scenario: 无效凭据
- GIVEN 无效凭据
- WHEN 用户提交登录表单
- THEN 显示错误消息
- AND 不颁发令牌
元素用途
## Purpose规范的用途与行为边界
## Requirements主规范的需求集合，不含 Delta 操作节
### Requirement:具体行为；冒号后名称与正文可以用中文
#### Scenario:带实际内容的可验证场景，使用四个 #
SHALL / MUST规范性正文关键词；建议保留，strict 模式仍要求

结构锚点保持英文：不要把 Purpose、Requirements、Requirement: 或 Scenario: 翻译成中文。普通 openspec validate 对正文缺少 SHALL/MUST 仅警告，不因此判失败；--strict 会因该警告失败。标题中有关键词不能替代正文。

规范的本质：规范是行为契约，而非实现计划。好的规范内容包括可观察行为、输入/输出/错误条件、外部约束。避免在规范中写内部类名、库或框架选择、逐步实现细节。

变更 (Changes)

变更是对系统的提议修改，打包为一个包含理解和实现所需一切的文件夹：

变更文件夹结构
openspec/changes/add-dark-mode/
├── proposal.md           # 为什么做、做什么
├── design.md             # 如何实现（技术方案）
├── tasks.md              # 实现任务清单（带复选框）
├── .openspec.yaml        # 变更元数据（可选）
└── specs/                # Delta 规范
    └── theme-preference/
        └── spec.md       # 对应 proposal 声明的新 capability
📦

一切在一起

提案、设计、任务和规范都在一处。无需在不同位置寻找信息。

⚡

并行工作

多个变更可以同时存在。共享主规范或需求时需协调，不保证合并无冲突。

📚

清晰历史

归档时，变更移至 archive/ 并保留完整上下文，方便日后追溯原因。

🔍

便于审查

变更文件夹易于审查——打开它，阅读提案，检查设计，查看规范 Delta。

.openspec.yaml 元数据：文件可省略；一旦提供，必须有可解析到现有工作流的 schema。布尔标记必须是 YAML 布尔值，不能写成字符串。

字段用途与约束
schema必填，工作流 schema 名称，如 spec-driven
created可选字符串，YYYY-MM-DD 格式
goal可选非空字符串，记录目标
affected_areas可选字符串数组，元素非空，记录涉及区域
initiative可选关联对象，仅接受 store 和 id；值为 kebab-case 标识符
skip_specs: true无行为变化的 refactor、tooling、docs 变更免写 Delta；specs/ 下不得有任何文件。按 generates 的 specs/ 路径前缀跳过产物，不按产物 id 判断
retire_capabilities: true授权在 REMOVED 移除最后一个需求时退休 capability，删除对应 live spec；安全检查仍须通过
x-*顶层工具扩展，OpenSpec 忽略且不警告；前缀必须小写 x-，后缀非空且无空白，如 x-tracker、x-jiraKey
无行为变化：openspec/changes/refactor-theme/.openspec.yaml
schema: spec-driven
created: "2026-10-01"
skip_specs: true
x-tracker: UI-42
移除 capability：变更 .openspec.yaml（配合 REMOVED Delta）
schema: spec-driven
retire_capabilities: true

未知键无效果：非 x-* 的未知顶层键在 validate 中产生 warning，--strict 因此失败。skip_design 不受支持。扩展约定不适用于 initiative 内部。

skip_specs ≠ archive --skip-specs：元数据声明没有规范行为变化，影响产物与验证；CLI 归档选项仅跳过该次主规范合并，不替代元数据，也不豁免 Delta 验证。

📄 Proposal — 提案文档 +

提案捕捉意图、范围和高层方案：

proposal.md 示例
# 提案：添加暗色模式

## Why
用户希望有一个暗色模式选项，以减少夜间使用时的眼睛疲劳。

## What Changes
- 添加主题切换、系统偏好检测与本地存储持久化。
- 不包含自定义颜色主题。

## Capabilities
### New Capabilities
- `theme-preference`：选择并保存亮色或暗色主题。

### Modified Capabilities
无。

## Impact
影响设置页与主题样式；技术选型写入 design.md。
📐 Design — 设计文档 +

设计文档捕捉技术方案和架构决策：

design.md 示例
# 设计：添加暗色模式

## 技术方案
主题状态通过 React Context 管理以避免 prop drilling。
CSS 自定义属性支持运行时切换而无需切换 class。

## 架构决策

### 决策：Context 而非 Redux
使用 React Context 的原因：
- 简单的二值状态（亮/暗）
- 无复杂状态转换
- 避免引入 Redux 依赖
✅ Tasks — 任务清单 +

每个复选框任务都写明验收方式：测试、命令、可观察行为或交付产物。实现与本组所需测试一起完成，不把测试全部留到最后。

tasks.md 示例
# 任务

## 1. 主题基础设施
- [ ] 1.1 创建亮/暗状态的 ThemeContext；运行状态切换单元测试
- [ ] 1.2 为颜色添加 CSS 自定义属性；检查两种主题的计算样式
- [ ] 1.3 实现 localStorage 持久化；测试刷新后保留选择
- [ ] 1.4 添加系统偏好检测；测试无保存选择时跟随系统主题

## 2. UI 组件
- [ ] 2.1 创建 ThemeToggle；通过键盘与鼠标切换组件测试
- [ ] 2.2 在设置页添加切换；验证页面主题即时更新
- [ ] 2.3 在 Header 添加快速切换；测试与设置页状态一致

## 3. 样式
- [ ] 3.1 定义暗色调色板；检查文字对比度达到项目标准
- [ ] 3.2 更新组件使用 CSS 变量；对两种主题运行视觉回归

Delta 规范

Delta 规范是让 OpenSpec 适用于已有项目改造的关键概念。它们描述正在变化的内容，而不是重新陈述整个规范。

Delta 规范格式示例
# Auth 的 Delta 规范

## ADDED Requirements

### Requirement: 双因素认证
系统 MUST 支持基于 TOTP 的双因素认证。

#### Scenario: 2FA 登录
- GIVEN 启用了 2FA 的用户
- WHEN 用户提交有效凭据
- THEN 呈现 OTP 挑战
- AND 仅在有效 OTP 后完成登录

## MODIFIED Requirements

### Requirement: 会话过期
系统 MUST 在 15 分钟不活动后使会话过期。

#### Scenario: 空闲超时
- GIVEN 已登录会话连续 15 分钟没有活动
- WHEN 用户再次请求受保护资源
- THEN 拒绝请求并要求重新登录

#### Scenario: 持续活动
- GIVEN 已登录会话每隔不到 15 分钟就有活动
- WHEN 用户请求受保护资源
- THEN 会话保持有效

## REMOVED Requirements

### Requirement: 记住我
**Reason**: 持久登录不再符合双因素认证的安全策略。
**Migration**: 用户在每次新会话中重新认证。

## RENAMED Requirements

- FROM: `### Requirement: 用户身份验证`
- TO: `### Requirement: 用户登录`
Delta 节含义归档时操作
## ADDED Requirements新行为追加到主规范
## MODIFIED Requirements变更的行为替换整个需求块及其场景
## REMOVED Requirements废弃的行为从主规范中删除
## RENAMED Requirements仅改名称；相邻两行 - FROM: `### Requirement: 旧名`、- TO: `### Requirement: 新名`重命名并保留正文与场景

操作头保持精确：不要给上述四个英文标题添加括号或中文后缀。ADDED 与 MODIFIED 必须有需求正文及至少一个非空 Scenario。

MODIFIED 复制完整块：先读取 live spec，从 Requirement 标题复制到全部场景结束，再修改行为。示例假定会话过期已有“空闲超时”和“持续活动”场景；实际变更必须保留当前需求的所有场景，不能只写新描述。若同时 RENAMED 与 MODIFIED，后者使用新名称。

Purpose 与主规范：新 capability 的 Delta 可先写 ## Purpose，创建主规范时沿用它。已有 capability 的 Purpose 要直接编辑所选根下的 openspec/specs/<capability-path>/spec.md，不是放进 Delta。主规范将需求和场景放在 ## Requirements 下，不应含四种 Delta 操作节。

提前 sync 不等于免检：已应用且内容一致的 ADDED/MODIFIED、已删除的 REMOVED、旧名消失且新名存在的 RENAMED 会按已同步处理，可为 no-op。ADDED 内容碰撞、缺失的 MODIFIED 目标、重命名碰撞或场景丢失仍会阻塞合并，不能靠“已 sync”跳过冲突。

Schema 机制

Schema 定义产物、输出路径、模板、指令与依赖，也定义 apply 的入口和任务跟踪。默认工作流为 spec-driven。

schema.yaml 结构摘录（非完整可运行 schema）
name: spec-driven
version: 1
artifacts:
  - id: proposal
    generates: proposal.md
    requires: []              # 无依赖，可以先创建

  - id: specs
    generates: specs/**/*.md
    requires: [proposal]      # 依赖 proposal 产物

  - id: design
    generates: design.md
    requires: [proposal]      # 可与 specs 并行创建

  - id: tasks
    generates: tasks.md
    requires: [specs, design] # 依赖 specs 和 design 产物

apply:
  requires: [tasks]
  tracks: tasks.md
proposal
根节点
specs
依赖: proposal
design
依赖: proposal
tasks
依赖: specs + design

摘录不是安装文件：完整 schema 的 version 必须为正整数，每个产物需要 description 与 template，模板文件也须存在。上例省略这些字段及 instruction 内容；自定义工作流应提供适合产物和 apply 的指令。

声明顺序：依赖决定何时 ready；同时 ready 的产物按 artifacts 列表声明顺序排列，不按字母排序。文件存在只满足规划依赖，不是内容验收。

apply 校验：未知 apply.requires id 在加载 schema 时直接报错。apply.tracks 与所有 generates 字符串都不完全相同时，openspec schema validate 给出 warning；即使 glob 实际覆盖 tracks 文件也会警告。这不阻止加载，但可能使任务进度回退到顶层 tasks.md。

完整工作流程

按所选 schema 的 instructions 创建产物并实现任务。以下是默认工作流，不能把固定文件名或箭头顺序套到所有自定义 schema。

1
启动变更
/opsx:propose 或 /opsx:new
↓
2
创建产物
proposal → specs → design → tasks
↓
3
实现任务
/opsx:apply
↓
4
核对实现与测试证据
可用 /opsx:verify 辅助检查；不替代实际测试
↓
5
归档变更
完成同步与检查后，将变更目录移至 archive/

任务勾选不是验证记录：只把 x/X 复选框计为完成，其他标记仍未完成。按 schema 解析真实跟踪文件与 glob，不能由 tasks.md 缺失或产物 done 推断任务完成。全勾选也不证明实现、测试或审查通过。

同步成功后再移动：选择同步时，遵循所选 schema 的 specs 指令与项目规则，等待 sync 完成并逐 capability 对照主规范。仅在没有 stop、blocking 或未应用差异时移动目录；已提前同步的变更仍需核对。用户明确选择跳过同步时，报告“sync skipped”，不要声称已合并。

失败时保全：sync 失败或报告 blocking 时停止归档，保留活跃变更目录。CLI 在写入前检查所有待合并规范及目标目录；写入或移动失败时尝试回滚已做修改。若并发修改阻止安全回滚，保留并检查报告的恢复路径，不覆盖他人修改。

归档日期：目录为 openspec/changes/archive/YYYY-MM-DD-<change-name>/，日期取本地时区，不取 UTC。变更名已有日期前缀则沿用，不重复加日期；目标已存在时停止。

CLI 选项边界：archive --skip-specs 明确跳过主规范合并。--no-validate 跳过验证，但不消除合并冲突，且不会执行 capability retirement；即使设置 retire_capabilities: true，也不能在无验证时据此自动删除 live spec。

术语表

术语定义
产物 (Artifact)变更中的文档（proposal、design、tasks 或 Delta 规范）

变更 (Change)打包为带有产物的文件夹的系统提议修改
Delta 规范描述变化（ADDED/MODIFIED/REMOVED/RENAMED）的规范
RENAMED以 FROM/TO 配对重命名需求，保留原有正文与场景
Store本机按名称登记的独立 OpenSpec 规划 repo，含 openspec/ 与 .openspec-store/store.yaml
